# ADR-0019: Lua 5.4 as the device's scripting language

Status: accepted (19 November 2026).

## Context
The shell runs commands and small scripts, but has no data structures, no functions and no arithmetic beyond `calc`. MicroPython
devices and the Lua-scripted competitors let their owners automate the device on the device. A scripting language in a WebAssembly
package needs setjmp (Lua) or a whole libc (MicroPython) that the SDK does not have.

## Decision
- **Lua 5.4.7** (MIT, `third_party/lua`, the official archive unchanged; SHA-256 `9fbf5e28...1e30`), built into the firmware as the
  `lua` command, not as a package: native C has setjmp, and Lua's core is small.
- **Only what fits the device.** The core and the base, string, table, math, utf8 and coroutine libraries, in a library of its own
  built for size (`-Os`). io, os, package and debug are left out: they use the C library's files and dlopen, not Nema. print,
  io.write, io.read, dofile and loadfile go through Nema instead, and a `pal` module reaches the system (files, the shell,
  settings, notifications, the buzzer; `docs/LUA.md`).
- **A citizen of the system.** Memory comes from `nema_alloc` (PSRAM first) with a cap of 1 MB per state, so a runaway script gets
  Lua's own "not enough memory"; a count hook checks Ctrl-C; C calls nest at most 64 deep (`LUAI_MAXCCALLS`) to fit the command's
  24 KB stack; only text chunks load. The runtime (`apps/lua_rt.c`) writes through a callback, so `test_lua` reads what scripts
  print.

## Consequences
- The firmware grows by about 118 KB, to 87.2% of the update slot: past the release's 85% warning (it fails at 95%). The next
  addition needs room: a size-optimised build, or larger update slots (a new partition table, written over the cable).
- Proven by `test_lua` and in the native simulator (scripts, the prompt with multi-line input, Ctrl-C, the memory cap); built for
  hhv2, not run there yet.
